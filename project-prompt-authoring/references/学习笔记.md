# Claude 提示工程最佳实践：二十部分完整回答



这份 [Claude 官方提示工程指南](https://platform.claude.com/docs/zh-CN/build-with-claude/prompt-engineering/claude-prompting-best-practices)的核心思想是：**把提示词当作一份任务说明，让模型知道要完成什么、为什么做、依据什么材料、遵守哪些边界，以及怎样判断结果是否可用。**

它覆盖的内容比“怎么写一句好提示词”更广，还包括工具调用、长任务管理、智能体行为、模型推理设置和 API 迁移。下面我按学习顺序整理，并标出哪些是通用经验，哪些依赖 Claude 的具体模型或运行环境。

> 本文的例子是我为了帮助理解而编写的，不是官方文档的原文，也没有针对不同模型进行对照实验。官方页面会更新，模型能力和 API 参数以实际使用时的文档为准。

---

# 一、先建立一个整体认识：提示词到底在解决什么问题？

可以把提示词看成你交给一位新同事的工作说明。

你知道自己的目标、业务背景、偏好和限制，但模型未必知道。如果只说：

> 帮我分析这个项目。

模型可能不知道：

- 你想了解产品能力，还是源码架构？
- 是只阅读，还是要修改？
- 应该关注整体设计，还是某个具体模块？
- 答案面向初学者，还是开发者？
- 哪些结论必须基于源码？
- 需要讲到什么程度？

因此，一个实用的提示词通常会涉及下面几个要素：

| 要素 | 要回答的问题 | 示例 |
|---|---|---|
| **目标** | 要完成什么？ | 分析项目的提示词优化机制 |
| **背景** | 为什么做？谁会使用结果？ | 我正在学习 Agent，希望理解设计思路 |
| **输入** | 基于哪些资料？ | 指定 GitHub 仓库和 README |
| **范围** | 重点看哪里？不需要什么？ | 重点讲架构和调用链，不逐行解释 |
| **约束** | 哪些事情要遵守？ | 区分源码证据和推测 |
| **输出** | 希望怎样呈现？ | 先总体流程，再举例 |
| **验收标准** | 什么样的结果算有用？ | 能说明入口、核心模块和验证方式 |

并不是每次都要把七项全部写出来。日常问题可能只需要一句话；当任务复杂、需要重复执行或后果比较重要时，这些信息的价值就会明显增加。

官方指南首先强调的也是**清晰、直接，并按需要补充背景**。它建议把提示词交给不了解任务的人阅读：如果这个人不知道要怎么执行，模型也可能产生类似的困惑。[官方指南：通用原则](https://platform.claude.com/docs/zh-CN/build-with-claude/prompt-engineering/claude-prompting-best-practices)

# 二、基础原则一：明确说出你想让它做什么

## 1. 用具体动作替代宽泛动词

“分析”“优化”“处理”这些词本身并不错误，但它们的含义很宽。

例如：

> 优化这个 Agent 提示词。

模型可能自行决定优化目标：增加角色设定、扩展任务步骤、改变输出格式，甚至加入你没有要求的业务规则。

更明确的写法是：

> 优化这个 Agent 的系统提示词。保留现有业务规则，重点解决两个问题：\
> 1. 检索不到证据时，模型仍会自行编造答案。\
> 2. 用户的问题包含多个子问题时，回答容易遗漏。\
>
> 请先指出原提示词中可能导致这些问题的部分，再给出修改版本和修改理由。不要假定修改后已经解决问题。

这段提示词增加了三个关键信息：

1. **问题是什么**：编造和遗漏。
2. **哪些不能改变**：已有业务规则。
3. **需要什么结果**：问题分析、候选版本、修改理由。

## 2. 区分“建议”和“执行”

对于具备文件、代码或其他工具的智能体，动词尤其重要。

| 你的真实意图 | 更清楚的说法 |
|---|---|
| 只想了解 | “分析这个函数有哪些性能问题。” |
| 想看方案 | “给出修改方案，暂时不要改文件。” |
| 希望直接修改 | “分析并修改这个函数，然后运行相关测试。” |
| 希望先研究再决定 | “先检查代码和测试，给出修改方案，等我决定后再实施。” |

官方指出，如果你问“能不能建议一些修改”，Claude 可能只给建议；如果希望它动手，需要明确说“修改”。[官方指南：工具用法](https://platform.claude.com/docs/zh-CN/build-with-claude/prompt-engineering/claude-prompting-best-practices)

**适用范围：**这不只是 Claude 特有的原则。只要使用带工具的 AI Agent，说明是“看”“建议”还是“执行”，都能减少误解。

# 三、基础原则二：告诉模型背景和目的

同一条规则，有时解释原因比只给命令更有用。

比如：

> 不要使用省略号。

这是一个格式规则，但模型不知道原因，也不知道遇到相似情况该如何处理。

如果写成：

> 这段文字会交给语音合成系统朗读。请使用完整句子，避免使用省略号或其他可能被错误读出的符号。

模型更容易理解你的真正目标：**让内容适合朗读**。

这不意味着每条指令都需要解释。解释原因特别适合：

- 你有特殊格式要求；
- 规则不是常识；
- 你希望模型在未列举的类似情况中自行判断；
- 任务涉及业务流程或实际使用环境。

### 结合你的学习场景

例如你希望我解释 Agent 源码：

**较模糊：**

> 解释这个 Agent 项目。

**加入背景后：**

> 我正在学习 Agent 开发，希望理解项目是如何组织 Agent 循环的。\
> 我能看懂基础 Python，但不想逐行阅读源码。请从架构、入口、一次请求的调用过程和验证方法四个角度解释，并标出关键源码位置。

这里的背景决定了讲解深度：不需要从 Python 语法开始，也不需要把每一行都罗列出来。

**需要注意：**给背景不是越多越好。与目标无关的大段背景会占用上下文，还可能让模型难以识别重点。

# 四、基础原则三：用示例告诉模型“什么叫做好”

官方把示例视为引导格式、语气和结构的重要方法。这通常称为**少样本提示**（Few-shot Prompting）：在正式输入之前，给模型几个“输入—期望输出”的例子。[官方指南：有效使用示例](https://platform.claude.com/docs/zh-CN/build-with-claude/prompt-engineering/claude-prompting-best-practices)

## 1. 为什么示例有用？

有些要求很难只靠抽象语言讲清楚。

例如：

> 请判断客服问题是否需要转人工。

“需要转人工”在不同业务中含义可能不同。通过例子可以说明边界：

```text
任务：判断客服问题是否需要转人工。

示例 1：
输入：我想查询订单什么时候发货。
输出：无需转人工。
原因：属于常规订单查询。

示例 2：
输入：我已经连续三次申请退款，但一直没有处理。
输出：建议转人工。
原因：多次处理失败，需要进一步介入。

示例 3：
输入：我要修改刚刚支付的订单地址。
输出：需要更多信息。
原因：是否能修改取决于订单状态。

现在处理：
输入：{{用户问题}}
```

第三个例子很重要。它告诉模型，结果不一定只有“是”或“否”，信息不足也是合法结果。

## 2. 什么样的示例好？

官方强调三个特点：

- **相关**：和实际任务接近。
- **多样**：包括不同类型及边界情况。
- **结构清楚**：让模型能区分示例和当前输入。

我会再补一个实践上的建议：**示例中的判断标准要一致**。如果两个非常相似的案例给出了相反答案，模型会更难判断你的真实标准。

## 3. 示例不是越多越好

示例过多可能带来：

- 占用上下文；
- 增加模型调用成本；
- 模型照搬示例的表面措辞；
- 只适应示例覆盖的情况。

因此，更好的方式通常是：

1. 先选少量有代表性的案例；
2. 特别加入容易判断错误的边界案例；
3. 留出一部分没放进提示词的案例用于测试。

最后一点很重要：如果你既用同一批案例修改提示词，又只用这批案例验收，可能只是让提示词记住了这批题，而不代表它能处理新问题。

# 五、基础原则四：用结构把不同内容分开

官方推荐在复杂提示中使用 XML 风格的标签，例如：

```xml
<instructions>...</instructions>
<context>...</context>
<examples>...</examples>
<input>...</input>
```

它的主要作用不是让模型获得某种特殊能力，而是帮助模型识别：

- 哪一部分是任务指令；
- 哪一部分是背景；
- 哪一部分是示例；
- 哪一部分是需要处理的数据。

## 示例：分析合同条款

```xml
<task>
从合同中提取付款相关条款。
</task>

<context>
结果供工作人员进行初步整理，不能替代专业审查。
</context>

<requirements>
1. 提取付款节点、金额或计算方式、付款触发条件。
2. 每项结论标明对应原文。
3. 合同未明确说明的内容标记为“未找到”，不要自行推测。
</requirements>

<document source="合同A">
{{合同正文}}
</document>

<output_format>
使用表格，列出：事项、提取内容、原文依据、待核实问题。
</output_format>
```

## XML 是必须的吗？

不是。

如果任务很短，普通自然语言通常已经足够：

> 根据下面的会议记录，提取待办事项、负责人和截止时间；没有明确提到的内容标记为“未说明”。

XML、Markdown 标题和编号列表，本质上都是组织信息的方式。结构应服务于阅读和识别，不必为了“显得专业”强行添加。

**还有一个重要边界：**XML 标签可以帮助区分内容，但它不是安全隔离机制。把不可信文本放进 `<document>`，不代表模型一定不会被其中的恶意指令影响；安全问题仍需权限控制、可信边界和测试。

# 六、基础原则五：角色有帮助，但不能替代任务和证据

官方建议可以在系统提示词中给 Claude 一个角色，例如“擅长 Python 的编程助手”。

角色的价值是提供一个**视角和职责范围**。

例如：

```text
你是一名代码审查助手，重点检查正确性、边界条件和潜在回归。
```

但如果只写：

```text
你是世界顶级的 Agent 架构专家。
```

它仍然不知道：

- 要审查哪个系统；
- 应关注哪些风险；
- 依据什么资料；
- 输出给谁；
- 如何区分事实与猜测。

所以，一个更实用的组合是：

```text
角色：你是一名 Agent 系统设计审查助手。

任务：分析给定架构设计中的关键风险。

关注点：工具权限、状态管理、失败恢复和评测方式。

证据要求：区分设计文档中明确说明的内容和你的推断。

输出：先给主要结论，再按优先级列出问题及建议。
```

**记住：角色是任务说明的补充，不是能力认证。**让模型扮演专家，不代表它真的掌握你的项目细节，也不代表结论已经过验证。

# 七、长文档怎么提问？

官方指南对长上下文提出了几个建议：

1. 将长文档或大量输入放在提示靠前位置；
2. 多份材料标注来源；
3. 把问题和具体任务放在材料之后；
4. 要求回答关联文档中的相关依据。[官方指南：长上下文提示](https://platform.claude.com/docs/zh-CN/build-with-claude/prompt-engineering/claude-prompting-best-practices)

可以用下面的形式：

```xml
<documents>
  <document id="1" source="需求文档">
    {{需求文档内容}}
  </document>

  <document id="2" source="现有设计">
    {{设计文档内容}}
  </document>
</documents>

<task>
比较需求和设计，识别设计中没有明确覆盖的需求。
</task>

<requirements>
- 每个结论标注对应的需求和设计依据。
- 如果只是表述方式不同，不要直接判定为缺失。
- 证据不足时标记“需要进一步确认”。
</requirements>
```

官方页面把“长材料在前、问题在后”作为建议，但不应理解为所有模型、所有 API 和所有场景都一定如此。对于实际应用，还要考虑系统消息、上下文缓存、模型版本和成本，并用真实任务验证。

## 关于“先引用原文，再给结论”

对于合同、论文、规范和长报告，这是一种很实用的思路：

```text
先找相关原文
    ↓
确认原文是否真的支持判断
    ↓
给出结论
    ↓
说明信息不足或冲突
```

但是，要求模型给出引文不等于引文一定准确。重要任务仍要核对：

- 引文是否真实存在；
- 有没有截断导致原意改变；
- 引用的是不是正确版本；
- 引文能否支持相应结论。

# 八、如何控制输出格式？

官方建议不要只告诉模型“不要什么”，也要说清楚“你希望它输出什么”。

例如：

**较弱：**

> 不要写得太乱。

**较清楚：**

> 先用一段话说明结论，再分别解释原因和适用边界；涉及比较时用表格，普通解释用连贯段落。

或者：

```text
请按以下结构回答：
1. 结论；
2. 支持结论的依据；
3. 仍不确定的部分；
4. 下一步如何验证。
```

## 1. 提示词风格可能影响输出风格

如果提示本身满是层层标题、加粗和列表，模型有时也会模仿这种结构。如果你希望得到自然段落，可以明确说明：

> 请用连贯的中文段落解释，只在比较项目或列出步骤时使用列表。

反过来，如果你希望快速扫描，就明确要求表格或分点。

## 2. “写 JSON”与真正的结构化输出不同

这是开发应用时特别重要的一点。

```text
请输出 JSON。
```

只是自然语言要求。模型可能仍然：

- 添加解释文字；
- 漏掉字段；
- 使用无效 JSON；
- 输出错误的数据类型。

当结果要被程序消费时，应考虑：

```text
提示词要求
    +
模型或 API 的结构化输出能力
    +
程序端 schema 校验
    +
失败处理
```

即使格式合法，也仍然需要检查**内容是否正确**。例如 JSON 中的 `price` 是数字，只说明类型符合要求，不说明价格是真的。

# 九、如何指导模型使用工具？

这是这份指南里与 Agent 关系最密切的部分。

## 1. 工具可用，不代表每次都会使用

假设 Agent 可以调用：

- 搜索工具；
- 文件读取工具；
- 数据库查询工具；
- 提示词优化 MCP。

你需要根据任务说明什么时候应使用哪个工具。

例如：

```text
回答涉及当前项目实现的问题时，先读取相关源码，
再根据实际代码说明；没有找到的部分标记为未知。
```

相比之下：

```text
你有很多工具，可以自行选择。
```

虽然给了能力，但没有帮助它理解关键触发条件。

## 2. 明确工具调用目标，而不只是工具名称

例如：

> 使用搜索工具。

模型不知道要搜什么、搜到什么程度。

更好的是：

> 查找该项目的官方文档和当前源码，确认 MCP 实际暴露哪些工具；如果只在文档中看到描述、没有检查实现，请标明证据范围。

这里说明的是**为什么用工具、要确认什么、如何报告证据**。

## 3. 不要把所有工具调用都写成“必须”

官方提醒：某些较新的 Claude 模型可能比旧模型更积极地使用工具。以前为了纠正“不愿调用工具”而加入的强烈措辞，迁移后可能导致过度调用。

例如：

```text
任何情况下都必须使用搜索工具。
```

可能让模型连简单计算、解释已给定文本时也去搜索。

更有针对性的写法是：

```text
当问题涉及可能变化的信息，或需要核对具体外部资料时，
使用搜索或文档工具；对已提供的完整材料直接分析即可。
```

这里可以提炼成一个实用原则：

> **约束触发条件，比不断强化“必须、始终、绝不”更重要。**

# 十、工具并行：什么时候快，什么时候会出错？

官方建议对**相互独立**的工具调用进行并行，而有依赖关系的操作应按顺序执行。[官方指南：并行工具调用](https://platform.claude.com/docs/zh-CN/build-with-claude/prompt-engineering/claude-prompting-best-practices)

## 可以并行

例如，同时读取三个彼此独立的文件：

```text
读取 README
读取配置文件
读取项目目录结构
```

它们都不依赖其他结果。

## 应该串行

例如：

```text
先查找配置文件位置
    ↓
再读取找到的配置文件
    ↓
根据配置运行对应测试
```

第二步的路径依赖第一步的结果，第三步又依赖第二步，不能为了速度猜测参数。

对于实际 Agent，可以这样写：

```text
相互独立的只读操作可以并行。
如果某个操作依赖前一步的结果，按顺序执行，
不要猜测缺失的路径、参数或资源标识。
```

需要注意，并行通常适合独立读取或查询；多个操作如果会修改同一份文件、数据库状态或共享环境，即使看起来互不相关，也要考虑竞争和副作用。

# 十一、关于“思考”：不等于要求模型把所有思维过程写出来

官方指南讨论了 Claude 的思考能力、`effort` 参数、成本和延迟。这个部分需要区分两个层次：

### 第一层：作为普通用户怎么提问？

你可以描述希望模型完成的**分析和验证行为**：

```text
请比较这两种方案的适用条件、主要风险和取舍，
最后说明在当前约束下推荐哪一种，以及哪些信息还不确定。
```

或者：

```text
完成后请对照以下验收标准检查结果，
并报告未通过或无法验证的部分。
```

这比机械地要求“把每一步内部思维全部输出”更实用。你真正需要的是可检查的**依据、结论、假设和验证结果**。

### 第二层：作为开发者怎么配置？

Claude API 中的思考配置、默认值、`effort` 可选项和适用模型会变化。官方页面对不同模型列出了差异，也提醒开发者查看对应模型指南。[官方指南：思考与推理](https://platform.claude.com/docs/zh-CN/build-with-claude/prompt-engineering/claude-prompting-best-practices)

所以不要把某个型号、某个版本的参数当成永久通用规则。实际接入时应：

1. 确认具体模型；
2. 查看该模型当前支持的配置；
3. 用真实任务比较质量、成本和响应时间；
4. 为输出和思考预留适当预算；
5. 在应用中正确处理返回的不同内容块。

## 思考越多一定越好吗？

不一定。

- 简单事实整理，过度分析可能只增加延迟。
- 复杂设计、代码排错或多步工具任务，适当的推理和验证可能很有价值。
- 即使模型进行了自检，也可能重复原有错误。

因此，比“所有任务都深度思考”更好的策略是：**让任务复杂度和验证成本匹配**。

# 十二、Agent 长任务：提示词要考虑状态，而不只是目标

普通问答可能一次完成，但 Agent 任务可能持续很久，甚至跨多个上下文窗口。

例如：

```text
阅读项目
→ 确认现状
→ 修改代码
→ 执行测试
→ 分析失败
→ 修复问题
→ 汇总结果
```

如果中间上下文被压缩或会话中断，Agent 可能忘记：

- 原始目标；
- 已经做过什么；
- 哪些测试失败；
- 用户明确禁止什么；
- 下一步应该做什么。

官方指南建议对长任务进行增量推进和状态记录。[官方指南：长周期任务](https://platform.claude.com/docs/zh-CN/build-with-claude/prompt-engineering/claude-prompting-best-practices)

## 可以记录什么？

```text
目标：
完成订单查询 Agent 的提示词修订。

已完成：
- 阅读当前提示词和工具定义。
- 整理了 20 个测试案例。
- 完成第一版修改。

已验证：
- 格式检查通过。
- 10 个离线案例已运行。

未完成：
- 工具异常场景测试。
- 信息不足场景复核。

限制：
- 不调用生产写接口。
- 不修改业务数据。

下一步：
使用测试环境运行剩余案例，并对比旧版结果。
```

对于程序需要读取的状态，可以用 JSON 等结构化格式；对于交接和理解，自然语言进度笔记往往更方便。

但这里有个前提：**提示词不能凭空创造环境能力。**

如果当前系统没有上下文压缩、持久化文件或记忆机制，你写“上下文会自动保存，请无限继续”并不会让它真的具备这些能力。提示必须与实际运行环境一致。

# 十三、Agent 自主性：明确哪些事可以做，哪些事需要停下来

Agent 不只是生成文字，它可能可以操作文件、运行代码、发消息或调用业务接口。因此，提示词需要说明行动范围。

例如：

```text
你可以：
- 读取项目文件；
- 在本地修改代码；
- 运行测试。

遇到以下情况先停下来：
- 删除可能影响他人工作的文件；
- 修改共享环境或生产配置；
- 发送消息或发布内容；
- 执行难以撤销的操作。
```

官方文档强调根据**可撤销性和影响范围**区分行为。例如，本地可恢复的修改与影响共享系统的操作，风险不同。

但也不要把所有事情都设计成“先问一次”。如果一个操作已经被用户明确要求，而且可逆、范围清楚，反复确认会降低协作效率。

这里值得记住的是：

```text
提示词中的授权说明
        +
工具本身的权限配置
        +
系统层面的安全控制
```

三者应当配合。不能只靠提示词说“不要修改生产数据”，却仍给 Agent 完全不受限制的生产写权限。

# 十四、子智能体：什么时候值得拆分？

官方讨论了让模型编排子智能体，也提醒某些模型可能过度委派。

例如，你让 Agent：

> 分析三个互不依赖的开源项目，分别总结能力和限制。

如果系统支持子智能体，可以拆成：

```text
主智能体
├─ 子任务 A：研究项目 A
├─ 子任务 B：研究项目 B
└─ 子任务 C：研究项目 C
        ↓
主智能体汇总比较
```

这适合：

- 任务之间相互独立；
- 每个子任务需要独立上下文；
- 可以并行；
- 最终需要统一汇总。

但如果只是：

> 查找一个函数定义。

创建子智能体可能比直接搜索更慢，还可能增加成本。

## 提示词如何描述？

```text
当工作可以拆成互不依赖的研究任务，
或需要隔离上下文时，可以考虑使用子智能体。

对于简单查询、单文件修改或强依赖前一步结果的任务，
直接处理。
```

是否真的能这样做，取决于你使用的 Agent 产品或框架是否提供相应能力；提示词本身不能创建一个不存在的子智能体工具。

# 十五、提示链：什么时候要把任务拆成多次调用？

**提示链**可以理解为：

```text
第 1 次调用：生成草稿
        ↓
第 2 次调用：按照标准审查草稿
        ↓
第 3 次调用：根据审查意见修改
```

官方指出，现在的模型可以在一次调用中完成很多多步骤任务，但如果你需要**检查中间结果、设置固定流程、记录每一步**，显式拆分仍然有价值。

## 举例：Agent 提示词优化

### 一次完成

```text
请审查并优化这个系统提示词。
```

适合：

- 任务比较简单；
- 对流程可控性要求不高；
- 希望快速得到建议。

### 拆成多步

```text
步骤 1：提取现有提示词中的业务规则和约束。
步骤 2：根据失败案例找出可能的问题。
步骤 3：生成候选版本。
步骤 4：检查候选版本是否改变原有规则。
步骤 5：运行测试案例并比较。
```

适合：

- 提示词用于正式业务；
- 不能丢失已有约束；
- 需要审计修改原因；
- 有测试集和验收标准。

但也要注意：如果每一步都由同一个模型完成，它可能重复自己的偏差。所以，“模型审查模型”能辅助发现问题，但不等同于独立验证。

# 十六、编码 Agent 的几个重要提示原则

官方指南专门讨论了编程智能体容易出现的问题，对我们平时使用 Codex、Claude Code 等工具也有参考价值。

## 1. 先看代码，再谈代码

例如：

```text
回答项目实现问题前，先读取相关文件。
区分代码中直接看到的行为与根据代码作出的推断；
无法确认的内容明确说明。
```

这能减少模型凭文件名、既有经验或想象来解释代码。

但“读了文件”也不等于已经验证运行效果。要区分：

- **静态检查**：代码看起来会怎样执行；
- **实际运行**：运行时观察到了什么；
- **生产表现**：在真实环境和真实输入下如何表现。

## 2. 避免过度工程化

例如，你只要求修复一个按钮的文案，却发现 Agent 顺手：

- 新增一个通用配置框架；
- 重构整个页面；
- 添加大量没有使用的抽象；
- 改动无关模块。

可以这样约束：

```text
只修改完成当前任务所需的部分。
优先沿用现有结构，不为假设中的未来需求新增抽象。
如果发现其他问题，先记录，不要顺手扩大修改范围。
```

但也不要把它理解成“永远不允许重构”。如果必要的局部重构是完成任务的合理前提，应根据实际情况处理。

## 3. 不要只为了通过测试而硬编码

例如，测试里有：

```text
输入：A
期望：B
```

错误的实现可能直接写：

```text
如果输入是 A，就返回 B。
```

它通过了这个测试，却没有实现真正的业务逻辑。

提示词可以要求：

```text
根据需求实现通用逻辑，不要针对测试样例硬编码。
如发现测试与需求冲突，请说明，不要通过绕过检查掩盖问题。
```

不过，这条提示也不能代替好的测试设计。还需要有代表性的输入、边界案例和对实际行为的检查。

# 十七、视觉、前端和高风险任务

官方指南还给了几个特定能力方向。

## 1. 视觉分析：让模型能看清细节

当图片中信息很小或很密集时，仅说“仔细看”可能不够。更有效的工作方式可能是：

```text
先看全图理解布局
    ↓
定位相关区域
    ↓
放大或裁剪
    ↓
读取细节
    ↓
与全图核对
```

这要求运行环境提供相应图像查看或处理能力。提示词只能提出需求，不能保证工具存在。

## 2. 前端设计：说清使用场景和设计目标

如果只说：

> 做一个好看的页面。

模型容易使用常见模板。更有帮助的信息包括：

- 谁使用；
- 页面最重要的任务；
- 品牌或视觉气质；
- 信息密度；
- 交互重点；
- 设备和可访问性要求。

例如：

```text
设计一个供客服人员使用的订单查询页面。
主要使用场景是桌面端高频查询，信息密度可以稍高，
但订单状态、客户信息和异常提示要容易区分。
风格专业、清晰，避免为了装饰牺牲操作效率。
```

这里的重点是**适合任务**。不是所有页面都必须追求复杂动画、独特字体或强烈视觉效果。

## 3. 高风险领域：提示词不是安全保证

官方页面以儿童药物剂量为例，展示了如何要求模型依赖可靠来源、在信息不足时转交专业人员，并根据不同模型提供不同指令。

可以从中学习的通用思路是：

- 高风险结论需要可靠依据；
- 信息不足时允许不直接回答；
- 应明确何时交给专业人员；
- 提示词之外还需要产品流程、工具和实际评估。

不要把指南里的某一段医疗提示词理解成“复制后即可安全上线医疗应用”。

# 十八、模型迁移：旧提示词不一定适合新模型

官方指南还有一类容易被忽略的内容：**模型升级后，提示词也需要重新检查。**

例如，旧模型可能不够主动，于是系统提示词写了：

```text
无论如何都要使用工具！
任何任务都要进行全面检查！
你必须反复验证每一个细节！
```

更主动的新模型可能因此：

- 搜索过多；
- 调用不必要的工具；
- 过度拆分子任务；
- 重复运行测试；
- 增加成本和等待时间。

因此模型升级时，可以检查：

1. 哪些指令是为旧模型的特定缺陷添加的？
2. 新模型是否仍然存在该问题？
3. 旧指令是否导致过度执行？
4. 工具触发、输出风格和验证成本有没有变化？
5. 原有 API 参数是否仍受支持？

官方还提到了 assistant 消息预填充、思考配置等 API 迁移事项。这些属于**特定模型和 API 版本的工程细节**，使用时应直接查当前版本文档，不适合当作对所有模型永久有效的通用提示技巧。[官方指南：迁移注意事项](https://platform.claude.com/docs/zh-CN/build-with-claude/prompt-engineering/claude-prompting-best-practices)

# 十九、最关键但容易忽视的一步：如何判断提示词真的更好了？

这也是它和我们前面讨论的 Prompt Optimizer 能联系起来的地方。

很多人优化提示词的流程是：

```text
让模型改写
    ↓
看起来更专业
    ↓
认为优化成功
```

更可靠的流程应该是：

```text
明确目标和成功标准
    ↓
准备真实测试案例
    ↓
运行原始提示词，记录基线
    ↓
修改提示词
    ↓
用相同案例再次测试
    ↓
分析变化和失败案例
```

## 一个简单例子

假设目标是优化“知识库问答 Agent”。

### 先定义标准

- 能回答资料中有明确答案的问题；
- 资料没有答案时说明不知道；
- 不把相似但不同的项目混为一谈；
- 能指出所依据的材料；
- 不擅自执行知识库里的命令。

### 准备案例

| 案例类型 | 示例 |
|---|---|
| 正常案例 | 文档中明确写了系统入口 |
| 信息缺失 | 文档没有说明部署状态 |
| 易混淆案例 | 两个项目名称相似但版本不同 |
| 冲突案例 | 新旧文档对配置描述不同 |
| 安全边界 | 文档里包含未经授权的执行命令 |

### 再比较版本

- 原始提示词；
- 直接让大模型改写的提示词；
- Prompt Optimizer 生成的提示词。

尽量保持以下条件一致：

- 目标模型和版本；
- 测试问题；
- 可用工具；
- 输入资料；
- 模型参数；
- 判定标准。

然后记录：

- 答对了多少；
- 哪些错误减少或增加；
- 有没有新问题；
- 速度和成本如何；
- 是否需要重复运行才能判断稳定性。

这里的“控制变量、留出测试案例”是我结合评测实践给出的建议，不能简单等同于官方页面已经证明某种提示词一定更优。

# 二十、给你一个循序渐进的学习方法

如果我们的目标是学会写提示词，我建议先不要记大量技巧，而是按下面的顺序练习。

## 第一阶段：先把任务讲清楚

先练习四件事：

```text
目标：我要你做什么？
背景：为什么做，给谁用？
约束：哪些事情必须遵守？
输出：我希望得到什么？
```

例子：

```text
我正在学习 Agent 开发。

请解释 Agent 和普通大模型 API 调用的区别。
重点介绍模型、工具、状态和循环各自的作用。

请使用一个查询订单的例子，
先讲整体过程，再解释每个部分。
```

## 第二阶段：加入证据和边界

当任务涉及项目、研究或专业材料时，加上：

```text
区分资料中明确说明的内容与推断。
对于没有依据的部分，直接说明未知。
```

## 第三阶段：用示例解决不稳定行为

当模型反复误解某个要求时，加入 1～3 个有代表性的例子，尤其是边界案例。

## 第四阶段：涉及 Agent 时再加工具规则

明确：

```text
何时使用工具？
哪些操作可以执行？
哪些事情需要停下？
失败后怎么办？
怎么验证？
```

## 第五阶段：用测试案例改进

观察真实失败，而不是预先堆积大量规则。每次围绕一个具体问题修改，然后重新测试。

---

最后可以用一句简化版模板帮助记忆，但不必机械套用：

```text
请完成【任务】。

背景：【谁使用、为什么做】。
输入：【提供什么资料】。
要求：【重点、约束、证据和边界】。
输出：【结果形式和详略】。
验证：【如何判断结果可靠】。
```
