# 项目提示词写作指南

帮助智能体利用已有任务和项目上下文，写出目标明确、结构清楚、行为可理解、方便后续调整的提示词。以用户要求、项目现有约定和实际运行方式为准。这里是写作指导，不替代项目原有的开发流程。

## 从已有上下文提炼写作要素

先判断本次提示词需要让目标模型完成什么，以及已有上下文中哪些信息影响它的判断：任务和职责、使用场景、实际输入、业务规则、输出对象及约束。优先使用已有信息；只有缺少影响提示词正确性的关键内容时才进一步核对或说明未知，不编造工具、业务规则或事实。

修改已有提示词时保留仍然适用的业务含义、模板变量、消息角色和输出约定。根据实际任务选择详略；标准化是让内容易读、易改、行为清楚，不是强行套满所有章节。

## 怎么写

1. **明确任务与职责。** 用具体动作说明目标、处理对象和职责范围。需要角色时说明它的工作视角；不要依赖空泛的专家人设代替任务要求。
2. **提供有用背景和输入。** 写明影响判断的业务目的、输入来源与变量含义，区分待处理数据和指令。解释重要规则的原因，帮助模型处理未逐项列出的相似情况。
3. **组织核心规则。** 按逻辑分段，把关键判断、必须遵守的约束和必要顺序写清楚。规则应具体、一致、可理解；优先正面描述期望行为，禁止事项在确有必要时明确写出。
4. **按需补充边界。** 对任务有意义时，说明信息缺失、证据冲突、工具失败、无法判断等情况的处理。需要依据资料回答时，说明证据及来源要求；不能凭空填补未知内容。
5. **说明输出。** 根据使用场景写清交付内容、结构、详略和格式；如果下游有固定字段或 schema，保持约定。模型输出格式要求不能代替程序校验。
6. **必要时加入示例。** 当规则或边界容易误解时，选择少量相关、多样且与规则一致的输入及期望输出；不杜撰业务标准，也不将示例当成唯一合法结果。
7. **有工具才写工具规则。** 依据实际能力说明何时使用、需要什么输入以及失败时怎么处理；区分建议与执行，不赋予不存在的工具和权限。提示文本不能替代权限控制。

可用标题、编号或语义清楚的 XML 风格标签组织复杂内容，按项目现有风格选择。标签只帮助区分内容，不构成安全隔离。不要为了结构化重复背景、堆砌无关细节或写出未经要求的步骤。

## 区分稳定规则与动态输入

按项目已有的消息结构安排内容：长期适用的职责、行为规则和输出约定通常放在项目承载这些规则的位置；每次变化的问题、材料、变量和工具结果放在对应的动态输入位置。系统消息、用户消息及工具消息的实际分工以项目实现为准，不因这份指南改变消息优先级或模板契约。同一规则已有明确归属时，不必在每个消息中重复；跨消息存在冲突时应梳理清楚。

## 可裁剪的结构参考

```text
任务与职责：[要完成什么，服务什么目的]
背景与输入：[必要场景、输入内容和变量含义]
工作规则：[核心判断和必须遵守的要求]
边界处理：[信息缺失、冲突或失败时的行为，按需填写]
输出要求：[结果应包含什么，格式与证据要求]
示例：[仅在能消除歧义时提供]
```

这是帮助构思的清单，不要求逐项填写，也不规定系统消息和用户消息必须放在同一处。评估器提示词按任务明确评价对象、标准、证据及无法判断时的处理。

## 改写示例

假设已有上下文说明：任务是从合同文本中提取付款条件，供人工初审；每项要附原文依据，未明确说明时标记为“未找到”；现有输入变量是 `{{contract_text}}`。原提示词是“分析合同付款条件”。可以整理为：

```text
任务：从提供的合同文本中提取付款条件，供人工初审。
输入：{{contract_text}}
要求：列出付款节点、金额或计算方式及触发条件，并附上对应原文；
      文本未明确说明的内容标记为“未找到”。
输出：按事项、提取内容、原文依据和待核实问题组织结果。
```

该示例展示如何把已知的目标、输入、规则和输出分开；字段和形式仅为示范，以项目既有契约为准。如果业务上下文没有给出判断标准、权限或输出格式，应保留未知或按实际需求确认，不能借示例自行设定。真实项目中稳定规则和动态输入也可能分别由不同消息承载。

## 写完后检查

围绕成稿检查：

- 任务、输入和预期输出是否让人看得明白？
- 规则和示例是否一致，有无改变已有业务含义或遗漏必要约束？
- 需要时是否说明了信息不足、冲突和失败的处理方式？
- 变量、消息角色、工具能力及下游输出格式是否符合现有约定？
- 每部分是否有实际作用，有无重复、无关或无法执行的要求？

结合任务需要开展已有测试或案例比较；只做静态检查时说明其范围，不宣称提示词效果已经改善。
