# Claude Skill 写作指南学习参考

基于 Claude 官方中文指南整理。内容按写作决策重新组织，并用项目例子说明怎么落地。示例和检查方法用于表达项目已经确认的任务、步骤与约束。项目材料决定业务规则、工具契约和实际执行方式。

## 01 精简指令与控制自由度

审阅每段时，问它会改变哪一步、哪项判断或哪个结果。如果删除这段后，Agent 仍能从项目现状得出相同做法，就可以删减。优先保留项目特有的词、容易误判的边界和必要的核对方式。

| 场景 | 适合怎么写 | 项目例子 |
| --- | --- | --- |
| 多种做法都能满足要求 | 给目标和判断依据 | 允许 Agent 结合本笔付款材料选择最有辨识度的证据 |
| 有常用路径，特殊情形可调整 | 给默认流程，并在分支处说明条件 | 先查已知单据编号；编号缺失时按项目现有的候选查询路径走 |
| 顺序或参数关系到结果 | 写明前置条件、参数和成功信号 | 核对待认额、目标可认余额，再按既有工具契约生成建议 |

这些例子只展示指令具体程度。项目的权限、业务判断和提交条件仍以实际规则为准。

## 02 命名与触发描述

用任务能力命名。检查名称是否能让维护者在列表里辨认，并符合目标运行环境对目录名和文件头的要求。描述至少能回答两个问题：能做什么、什么请求适合使用它。写法可以用「生成可供人工核对的认款建议。适用于指定的银行收入流水及相关单据查证」。

审阅时选两条相近请求。比如「帮我核对这笔银行到账对应哪张单据」和「解释认款是什么意思」。看描述能否让 Agent 选中第一条、把第二条交给普通问答。工作流步骤、工具参数和业务例外进入正文。

## 03 入口与参考文件

先写入口能独立完成的常用路径，再画出读文件的分支。每个分支说明触发条件、文件位置、要查的内容，以及读完回到主流程的哪一步。

| Agent 何时需要 | 内容例子 | 放置位置 |
| --- | --- | --- |
| 每次都需要 | 输入范围、共同证据要求、结束条件 | `SKILL.md` |
| 某个业务分支才需要 | 押金凭证、代付关系、销售单据特例 | 对应本地参考 |
| 操作复杂但可重复 | 抽取字段或重算金额 | 现有工具或随 Skill 提供的脚本 |
| 生成成果时才用 | 固定模板、示例表、素材 | 随成果步骤引用的资源 |

入口直接链接到最终需要的文件，长参考在顶部给目录。每条共用规则选一处维护，别在三个分支各保留一份近似文本。划分标准是任务中哪些内容需要一起读。短 Skill 可以只用入口。

Anthropic 的 PDF 示例提供一个对照。常用处理在入口介绍，填表任务转到专项说明，深入细节再查参考。项目里的代付规则可以用类似的读取条件。

## 04 复杂流程与反馈

按可检查的中间结果写步骤。例如先拿到候选单据，再核对原始材料，最后生成建议并复核。每一步给出足以进入下一步的结果。对失败分支说明该补查、修正输入，还是保留人工核对线索。

一个实用的检查方法是从最后一步倒推。若「输出建议」依赖已核实的付款范围，前面的流程应给出明确的核对位置。若工具拒绝字段，应回到填参处修正并复核；若业务证据不足，则走项目已有的保守分支。把校验结果和下一步动作写在一起，避免只写一句「出错请重试」。

## 05 术语模板与示例

同一个对象在正文、参考和示例中使用相同名称。例如区分「本笔待认金额」「目标可认余额」「本次分配金额」。项目约定或 API 会更新时，指向当前维护位置，历史说明单独标注适用版本。

- 固定接口字段或法定格式可以给严格模板，并注明哪些字段不能改。
- 报告结构或用户文案可以给默认示例，允许按任务调整。
- 判断难点适合用成对用例。例如同金额且有可靠关联依据，与同金额但缺少关联依据。例子重点写出导致结果不同的那条证据。
- 多个选项能达到同一结果时，先给项目里的常用路径，明确什么情况下才切换。

Markdown 版式以仓库规范为准。常见做法是用动作标题、短段落和适量表格；如果一个表格单元需要解释几条例外，改成小节更好找。

## 06 评估与迭代

把验证分成三个观察点：是否选中了 Skill、是否读到了该读的材料、是否执行了正确动作。失败时先定位在哪一层。改描述解决发现问题；把链接放到正确的决策点解决漏读；修改判断表达或增加关键例子解决读了仍做错的问题。

新 Skill 可以在未加载时先跑代表任务。已有 Skill 调整时，保留当前版本的行为作为对照。让测试执行者用真实入口做任务，记录实际工具调用、读取文件和结果。将观察交给修改者，针对问题调整，再用同样的案例回放。计划支持不同模型时，在实际拟用模型上检查代表用例。

认款示例可用直接证据充足、只有同名同额、候选查询不完整三类案例。逐条记录应输出什么、实际读到了什么、实际输出什么。用例通过只说明覆盖的行为，未运行的分支单独保留。

## 07 脚本工具与运行环境

可机械处理的操作优先复用现有工具，例如读取字段、计算合计或检查结构。为脚本写清输入、输出和失败信号，并提供实际可检查的结果。依赖按项目环境管理，确认工具确实可用。涉及 MCP 时，使用目标框架注册的完整工具名。Skill 内部文件路径用相对路径和正斜杠。

对需要人工核对的复杂成果，可以保留可检查的中间输出。例如提取 PDF 表单时，先生成字段位置清单，再按清单检查映射；布局或图形结果可用预览图检查。对写入或其他有副作用的动作，沿用项目的校验、授权和确认方式。

## 08 技术约定与交付检查

通用 Skill 入口使用 YAML 文件头和 Markdown 正文。先核对目标项目支持的字段、命名规则和发现位置。Claude 指南的行数建议可作为审阅信号：入口变长时先查有哪些按需内容能拆；参考变长时加目录，帮助 Agent 跳到对应小节。

- 发现：名称、描述、目录符合目标项目，典型任务能看出适用范围。
- 结构：常用任务有清楚入口，关键约束读得到，分支引用可以直接到达。
- 内容：词汇一致，示例具体，旧规则和接口契约经过核对。
- 执行：现有工具和依赖可用，必要的中间结果可核验。
- 验证：区分文件检查和行为复测，说明覆盖了哪些任务和模型。

在实际部署前，再按目标环境确认安装、发现和使用方式。
