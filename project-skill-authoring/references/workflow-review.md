# 原文核对与复测记录

先核对改写是否保留原文规则。若文档调整会影响 Skill 的触发、关键分支或参考读取位置，再用后面的模板记录前后行为。必要时用 `writing-skills` 组织复测。

## 原文规则对照

逐条记下「原文规则 → 新稿位置 → 核对结果」。一条规则如果同时规定条件、动作和禁止的推断，把这些要求一起核对。

| 原文规则 | 核对新稿 |
| --- | --- |
| 读取失败时标记未知，不能把失败当成没有记录 | 新稿同时写明如何标记以及禁止得出的结论 |
| 仅对已确认的结果使用某个字段 | 新稿保留限制条件，并核对原文是否规定了其他情况的处理 |
| 工具只校验字段格式，语义由 Agent 判断 | 新稿保留双方职责，避免把工具通过写成业务结论成立 |

检查发现缺失时，先改稿。原文之间有冲突或含义不清时，记录待确认。

## 定义案例

| 项目 | 填写内容 |
| --- | --- |
| 变更 | 哪条规则、哪个链接或哪项触发说明发生变化 |
| 输入 | 用户请求、已知材料和工具可用情况 |
| 预期路径 | 是否应触发 Skill，应该读什么，应该完成什么动作 |
| 对照 | 修改前版本的结果；新 Skill 可用未加载时的结果 |
| 验收 | 用实际输出、工具调用或可见轨迹能核对的条件 |

## 记录运行结果

| 案例 | 前后版本 | 观察到的读取与动作 | 实际结果 | 结论 |
| --- | --- | --- | --- | --- |
| 受影响的正常路径 | 各记录一次 | 读到的规则、用到的工具 | 实际交付或状态 | 通过、失败或无法核实 |
| 相邻或异常路径 | 各记录一次 | 是否误触发、漏读或错误继续 | 实际交付或状态 | 通过、失败或无法核实 |

按任务需要选择案例。若运行环境只返回最终结果，把读取情况标为无法核实。

## 示例

若将代付规则移到本地参考，可选一笔有可靠代付依据的流水和一笔只有同名同额的流水。前者观察 Agent 是否在分配前找到代付规则；后者观察 Agent 是否沿用既定预填门槛。记录依据和输出各自是否符合预期。
